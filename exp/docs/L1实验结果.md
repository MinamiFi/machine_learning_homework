## 0. 一句话结论

**打分网络（B2）在全部三个长度上都显著优于所有零成本基线**，跨长度 CR 0.7667 vs 最强零成本基线 LEN 的 0.5555。但**「优势随历史变长而扩大」这个说法只对零成本基线成立，对纯检索（B1）不成立**——B2/B1 比值 1.43× → 1.92× → 1.60× 非单调。另外**两阶段系统（B2R）接近纯检索**，说明当前向量检索的召回是整条链路的天花板。

**R1 与 B0 完全相同**（0.4333 / 0.1333 / 0.0111）——不是 bug，是必然：没有记忆模块时，"全量上下文"在超预算后就是按时间序从头截断，这恰好就是「越早越重要」。所以 **B0 相对 R1 没有任何信息优势，只是更贵**。

## 2. 三个关键发现

### 2.1 优势随长度扩大：只对零成本基线成立

| L | B2 / B1 | B2 − B1 | B2 / R0 | B2 − R0 |
|---|---|---|---|---|
| 128 | 1.47× | +0.311 | 1.96× | +0.478 |
| 256 | 2.00× | +0.400 | 5.13× | +0.644 |
| 512 | 1.96× | +0.278 | 5.11× | +0.456 |

**修正前（v1 文档）这里写的是 1.64× → 2.30× → 3.06×，即"优势随 L 单调扩大"。修正数据后这个结论不成立了**：比值 1.47 → 2.00 → 1.96，绝对差 0.311 → 0.400 → 0.278，两者都在 L=512 回落。

如实表述：**B2 在各长度稳定领先，且领先幅度在 L≥256 后不再增长**。相对位置基线 R0 的倍数确实是单调上升的（1.96 → 5.13 → 5.11，后两个几乎持平），但那是因为 R0 自己在长历史上崩了（0.500 → 0.156 → 0.111），不是 B2 变强了。

**L=512 时 B2 的 CR 只有 0.567，是当前最明显的短板。** 报告里必须交代这一点，而不是只报 L=128 的 0.978。

### 2.2 两阶段（B2R）被检索召回卡死——这是必须报告的负结果

B2R 的 CR 在所有长度上都接近 B1，远低于 B2。原因不是打分器不行，而是**needle 根本没进候选池**。

在 L1 的真实场景里实测 needle 的检索召回率（`top_m` 为候选池大小，needle 在库内的余弦排名）：

| L | 库大小 | top_m=10 | top_m=20 | **top_m=50** | top_m=100 |
|---|---|---|---|---|---|
| 128 | 128 | 0.3111 | 0.4000 | **0.6778** | 0.9667 |
| 256 | 256 | 0.2444 | 0.3222 | **0.4556** | 0.6889 |
| 512 | 512 | 0.1333 | 0.2444 | **0.3444** | 0.5000 |

**B2R 的 CR 与 needle 召回率一一吻合**（top-50：0.6778 → 实测 CR 0.6333、0.4556 → 0.4556、0.3444 → 0.3111）。这不是巧合，而是**上界被卡死**的直接证据：池外的 needle 打分器给 `-inf`，永远选不到。

注意召回率随库变大而下降——库越大，needle 越难挤进固定大小的候选池。所以「检索 top-50」这个设计在 L 增大时**越用越差**，与题目「长上下文优化」的目标正好相反。

**结论**：题目的设计（向量检索 + 神经网络打分）在当前配置下受检索召回限制。改进方向有三：
1. 提高 top_m（但 token 开销随之上升）；
2. 用更好的检索器（本项目用 all-MiniLM-L6-v2，容量很小）；
3. 打分器直接对全库打分（B2 的做法），检索只用于加速——这需要打分器足够快，实测 8,372 段 batch 推理 **0.014 秒**，完全可行。

这条要写进报告的"局限与改进"。

### 2.3 消融三因素全部无显著影响——也是个真实发现

位置基线 AUC = 0.8172（test），3 seeds 网格总耗时 408 秒。

**解释**：AUC 在 0.9336–0.9352 之间，跨度 **0.0013**，与 seed 间标准差（0.0001–0.0008）**同量级**。说明这个任务对模型容量完全不敏感——384 维 MiniLM 向量里，判别所需的信号是**近似线性可分**的，1 层就够。

这恰好呼应题目「**浅层**全连接神经网络」的设定：不是妥协，是这个任务本来就只需要浅层。**1 层（99,585 参数）是性价比最优配置**，比默认的 2 层少 40% 参数、AUC 还高 0.0012。

`weight_decay` 四个取值**小数点后四位完全相同**（0.9340），连标准差都一样（0.0007）——说明早停（best epoch 5）在任何正则强度下都先触发，L2 正则根本没机会起作用。这不是"调参无效"，是**训练在过拟合发生前就停了**。

## 3. 位置偏置的自查（重要）

打分网络 AUC 0.9332，但位置基线就有 0.8172。必须确认它不是在复现位置启发式。

**实测相关系数（test 全量 8,372 段）**：

| 量 | 值 |
|---|---|
| `corr(score, rel_pos)` | **−0.6312** |
| `corr(score, n_tokens)` | **+0.6331** |
| `corr(rel_pos, label)` | −0.5456 |

**两个相关性都高达 ±0.63，这是修正数据后新出现的现象**（v1 时 `corr(score, n_tokens)` 只有 +0.188）。原因是 system 错位修正后，每段记忆变成「本轮提问 + 本轮回复」，信息密度更高、长度差异更能反映信息量。

位置相关性 −0.63 看起来高，但**标签本身与位置的相关性就有 −0.546**——模型只是部分复现了任务固有的偏置。关键证据是分层 AUC：在每个位置区间内部，模型仍有判别力：

| 位置区间 | 样本数 | 正例率 | 模型 AUC |
|---|---|---|---|
| [0.00, 0.25) | 2,186 | 0.819 | **0.8986** |
| [0.25, 0.50) | 1,760 | 0.748 | **0.8628** |
| [0.50, 0.75) | 1,969 | 0.664 | **0.8545** |
| [0.75, 1.01) | 2,457 | 0.131 | **0.9220** |

若模型只学了位置，区间内 AUC 应退化到 0.5。实测最低 0.855，说明它在读内容。

按长度分层（四分位）：

| 长度区间（token） | 样本数 | 正例率 | 模型 AUC |
|---|---|---|---|
| [3, 25] | 2,024 | 0.135 | 0.9464 |
| [25, 36] | 2,047 | 0.532 | 0.9084 |
| [36, 48] | 2,127 | 0.752 | 0.8675 |
| [48, 152] | 2,174 | 0.816 | 0.8556 |

短片段更容易判（0.946），长片段更含糊（0.856），但**所有区间都远高于 0.5**，说明长度也不是唯一依据。注意长度与正例率强相关（短片段正例率 0.135、长片段 0.816）——因为修正后"用户提问 + 系统回复"完整的轮次更长，而这类轮次更可能有状态变化。

**但要如实报告**：模型确实**部分**利用了位置和长度。这一点在 L1 里的表现是 B2 在 L=128 拿到 CR=0.978——接近完美，可能因为短历史下位置与内容信号高度重合。

## 4. 实验设计上踩过的四个坑（都影响了结论）

写进报告的方法论部分，说明"结论是修正后才成立的"。

### 坑 1：query 取最后一轮 → 100% 是空话

MultiWOZ **1000/1000** 段对话以 `none` 或客套话结尾。第一版直接把最后一轮当 query，得到的是 `"none"` 或 `"Thank you for using..."`，整个 L1 失去意义。

修法：用**数据驱动**判据（`delta` 非空）而非关键词匹配。关键词会漏掉 `"I am sure. Thank you so much."` 这类混合句。

### 坑 2：主对话轮次全挤在开头 → 位置基线凭空获胜

第一版混排用「每个位置 50% 概率优先放主对话轮」，结果主对话的 7 轮在前 14 个位置就放完，后面 240 轮全是干扰。所有相关轮挤在开头，R0 的 Recall 高达 **0.812**。

修法：主对话轮次**等距铺开**（相关轮相对位置均值从 0.06 变为 0.458，接近均匀）。

### 坑 3：干扰轮 turn_idx 分布不匹配 → R0A / LEN 假性领先

主对话的相关轮天然集中在对话前几轮（首因偏置），而干扰轮均匀取自各轮次。于是 `-turn_idx` 和长度基线凭空拿到 0.5+ 的 CR。

修法：干扰轮只从 `turn_idx` 落在主对话历史范围内的轮次里抽。修正后相关轮 turn mean=3.04、干扰轮 3.16（匹配）；R0A 的 CR 从 0.533 降到 0.304。

### 坑 4：LEN 基线符号写反 → 差点得出相反结论

第一版把长度基线写成正数（越长越重要），但它是可疑基线，需要检验。修正后 LEN 仍很强（跨长度 CR 0.5555，**仅次于 B2，超过 B1 与 B2R**），说明长度确实是一个强信号——报告里必须交代，否则会让人怀疑打分器只学了长度。

自查：`corr(score, n_tokens) = +0.6331`，与位置相关性（−0.6312）量级相同，但两个方向的分层 AUC（位置 0.855–0.922、长度 0.856–0.946）都证明内容有效。

## 5. 预算扫描：压缩率对结论的影响

默认 B=2048 在 L=128 时相当于保留 45.5% 的历史——"压缩"没真正发生。补测了预算扫描（`exp/runs/20261124_093413_budget/budget_sweep.json`，`n_per_length=20`、seeds [0,1]，205 秒）：

| 预算 B | L=128（库 4,497） | L=256（库 8,910） | L=512（库 16,874） |
|---|---|---|---|
| 256 | 0.350 / 0.150 / 0.050（5.7%） | 0.100 / 0.125 / 0.000（2.9%） | 0.050 / 0.075 / 0.025（1.5%） |
| 512 | 0.475 / 0.275 / 0.100（11.4%） | 0.350 / 0.225 / 0.050（5.8%） | 0.225 / 0.100 / 0.050（3.0%） |
| 1024 | 0.875 / 0.350 / 0.150（22.8%） | 0.625 / 0.275 / 0.125（11.5%） | 0.400 / 0.275 / 0.075（6.1%） |
| 2048 | 1.000 / 0.700 / 0.425（45.5%） | 0.900 / 0.325 / 0.200（23.0%） | 0.625 / 0.275 / 0.100（12.1%） |

每格是 **B2 / B1 / R0** 的 CR，括号内是保留比例。

**结论要分开说**：

- **B=1024 与 B=2048 的 6 个格子，B2 全部第一**，且压缩越激进优势越大（L=512、B=1024：0.400 vs 0.275 vs 0.075）。
- **B=256 的 3 个格子里有 2 个 B2 输给 B1**：L=256 时 0.100 vs 0.125、L=512 时 0.050 vs 0.075。这是真实负结果——**预算只够放 8–9 个片段时，稠密打分器的排序精度不如余弦相似度**。可能原因：打分器学的是"片段整体重要性"（与 query 无关的绝对判断），而余弦相似度直接对齐 query，极低预算下后者更不容易选错。这个现象值得在报告里单独讨论。
- **R0 在全部 12 个格子里都最差或接近最差**，位置启发式在压缩场景下完全失效。
- **L=512、B≤512 时所有方法都接近 0**（保留 1.5%–3.0%），此时任何选择器都救不回来，是「关键信息在极低预算下无法保障」的负结果。

**报告的推荐配置**：L=512 时 B=2048（保留 12.1%），B2 的 CR=0.625，相比 B1 的 0.275 是 2.3× 提升。

## 6. 文档数字的自检

文档里每个数字都可以一键重算（**156 项，0 不一致，约 20 秒**）：

```bash
source exp/env.sh
python3 exp/scripts/verify_docs.py          # 全查
python3 exp/scripts/verify_docs.py --quick  # 跳过检索召回，约 15 秒
```

脚本里 `EXPECTED` 表登记了本地重算的项（相关性、分层 AUC、检索召回、needle 唯一支撑），`EXPECTED_FROM_RUNS` 登记了从 `runs/` 读出的项（L1、消融、反事实、necessity、JGA），逐项比对，不一致就 `FAIL` 并返回非 0。
**改了文档的数就要改对应的表**，否则这个检查会失效——这是它唯一的使用约束。

写这份文档时它抓到过三个错误：
1. `corr(score, rel_pos)` 我写 −0.679，实测 **−0.6312**；
2. `corr(score, n_tokens)` 我写 0.383，实测 **+0.6331**；
3. 「needle 召回率 0.100/0.178/0.389/0.644」那组数是**把 B2R 的 CR 抄成了召回率**——实际 L=256 的召回率恰好也是 0.389，纯属巧合，L=128/512 就完全对不上。

第 3 条最值得记：**两个不同的量碰巧数值相同**，只对一组数字做交叉验证是抓不出来的，必须三个 L 全对。

另一个坑：`hist.position_auc` 是 **val** 上的位置基线（0.8065），test 上的 0.8172 要单独按 `-rel_pos` 算，**两个数不能混用**。文档里两个都出现，自检里也是分开登记的两个键（`scorer.val_position_auc` / `scorer.test_position_auc`）。
