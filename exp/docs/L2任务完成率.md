# L2 任务完成率评测

> 这一页回答题目要求的三件事：**任务完成率**、**token 消耗**、**关键信息召回率**。
> 与 L1 的分工：L1（[`L1实验结果.md`](L1实验结果.md)）只看「选得对不对」，不需要 LLM，秒级、可跑全量；
> L2 真的让 LLM 读选出来的上下文去答题，才能给出任务完成率，但要花 API 钱。
>
> 数据：test split，90 个场景（L=128/256/512 各 30 段对话 × 1 seed），每场景问 2 个槽位 = 180 条
> backbone：`api:DeepSeek-V4.1-Flash`（`reasoning_effort=none`）
> 预算：B=2048 token
> 产物：`exp/runs/20261124_094210_eval_l2_l2_main_api2/L2_generation.json`
> 耗时：1,685 秒（约 28 分钟）

## 0. 为什么三个指标必须一起报

单看任何一个都会得出错的结论：

- 只看**任务完成率**：ORACLE 只有 216 token 就拿到 72.2%，会以为「把上下文压到最短就行」——但 ORACLE 是作弊基线（它知道哪些轮次属于本对话），真实系统做不到。
- 只看 **token 消耗**：B0FULL 用了 7,277 token，看起来「信息最全」，实际任务完成率 4.4%，全场最低。
- 只看**召回率**：B0FULL 的 CR 是 1.000（needle 100% 在上下文里），但答对率只有 4.4%。

**这三个数放在一起才说明问题**：needle 在不在上下文里（CR）和模型能不能答对（slot_acc）之间隔着一条巨大的鸿沟，而那条鸿沟就是「记忆过滤」这件事真正要解决的东西。

## 1. 主表

`slot_acc` = 逐槽位答对率；`scenario_success` = 场景内全部槽位答对（最接近 JGA，但每场景只有 2 个槽位，**不能当 JGA 报**）；`ar` = 在「ORACLE 能答对的 152 个槽位」上的答对率（**可答子集准确率**）；`ctx` = 实际进上下文的 token 数；`cr` = needle 是否被选入。

## 2. 配对比较（B2 减对照，按场景×槽位配对，bootstrap 5000 次）

| 对比 | 差值 | 95% CI | p | 结论 |
|---|---|---|---|---|
| B2 − B1 | +0.0222 | [−0.0667, +0.1111] | 0.6964 | **不显著** |
| B2 − B0 | +0.0611 | [−0.0224, +0.1500] | 0.1948 | 不显著 |
| **B2 − R0** | **+0.1667** | **[+0.0889, +0.2444]** | **<0.0001** | **显著** |
| B2 − R1 | +0.0500 | [−0.0335, +0.1389] | 0.3092 | 不显著 |
| B2 − R2 | +0.0722 | [−0.0111, +0.1556] | 0.0984 | 边缘，不显著 |

**必须如实写的一条**：B2 相对 B1（纯余弦检索）只高 2.2 个百分点，**p=0.70，不显著**。180 条样本的统计功效不够分辨这个量级的差异。**B2 唯一显著赢的是位置基线 R0（+16.7 个百分点，p<0.0001）**。

这与 L1 的结论一致：L1 里 B2 的 CR 0.7667 vs B1 的 0.4778（差 28.9 个百分点）是**巨大的**，但 CR 高不等于答对率高——因为选进来的干扰轮会污染答案（见 §4）。

**L=512 时 B1 的 slot_acc（0.3478）反超 B2（0.3043）**，但 B2 的 scenario_success 更高（0.1304 vs 0.0870）。这是 L1 里已见过的现象的另一面：长历史下 B2 的 CR 只有 0.4783，与 B1 的 0.3913 差距收窄，选择优势不足以抵消干扰轮带来的噪声。

**ORACLE 在三个长度上都是 0.85 / 0.72，且 token 数几乎不变（216 / 216 / 246）**——它只用本对话的真实历史（平均 6–11 轮），与人为加进去的 128/256/512 段干扰完全无关。这直接说明：**任务难度不来自「历史长」，而来自「历史里有别的东西」**。

## 4. 最关键的发现：ORACLE 216 token 84.4% vs B2 1,489 token 37.8%

这是本次实验最有信息量的数字对比，值得单独拆开。

### 4.1 不是「没选到」

抽查 4 个 L=128 场景（`MUL0003`/`MUL0004`/`MUL0011`/`MUL0014`），B2 选中 45–49 段 / 2,010–2,047 token，其中主对话轮次 5/6、5/5、8/11、6/6 段，**needle 全部被选中**。30 个 L=128 场景里主对话段只被漏选 36 段。

### 4.2 是「选到的干扰轮把答案带偏」

30 个 L=128 场景里有 **33 个（场景,槽位）组合**的选中上下文含「同槽位、不同值」的冲突干扰轮。例如：

- `hotel-area`：gold = `centre`，上下文里另一段对话说 `north`，模型答 `north`
- `hotel-stars`：gold = `0`，另一段对话说 `4`，模型答 `4`

**打分器无法知道某轮属于哪段对话**——这是纯文本打分的固有盲区。它能判断「这一轮在它自己的对话里重不重要」，但判断不了「这一轮对当前 query 是不是噪声」。

### 4.3 B0FULL 是最直接的证据

B0FULL（题目字面义的「原始全量上下文」，7,277 token）的 slot_acc 只有 **0.3222**，比 B2 的 0.3778 还低，比 ORACLE 的 0.8444 低 **52 个百分点**。而且它的 token 数是 ORACLE 的 34 倍。

**上下文越长、干扰越多，强模型也会被带偏。** 这就是「记忆过滤」这件事存在的理由——不是为了省 token（虽然确实省了 34 倍），而是因为**不滤会答错**。

### 4.4 这个差距的诚实解读

ORACLE 是**作弊基线**：它知道 `dialogue_id`，直接筛掉所有干扰轮。真实系统没有这个信息（或者说，如果有，问题就不存在了）。

所以正确的表述是：

> ORACLE 与 B2 的 46.6 个百分点差距，**不是「方法还不够好」，而是「任务本身有多难」的上界**。它说明：如果能把跨对话的干扰轮完美剔除，同样 216 token 就能到 84.4%。当前的打分网络做到了 37.8%——**中间那 46.6 个百分点，就是「区分对话归属」这件事的价值**。

这也直接指向改进方向：打分器目前只输入「单轮文本的句向量」，**看不到对话边界**。加一个 `dialogue_id` 的特征（或做对话级聚类）可能比调网络层数有用得多。这一点已写入根 README 的「局限与改进」。

## 5. token 消耗的实际含义

| 选择器 | ctx tokens | 相对 B0FULL | slot_acc |
|---|---|---|---|
| ORACLE | 216.1 | **3.0%** | 0.8444 |
| NEEDLE | 38.9 | 0.5% | 0.3444 |
| B1 | 1,457.7 | 20.0% | 0.3556 |
| B0 | 1,482.2 | 20.4% | 0.3167 |
| **B2** | 1,488.9 | 20.5% | **0.3778** |
| B0FULL | 7,276.6 | 100% | 0.3222 |

B2 把上下文压到 B0FULL 的 **20.5%**，同时 slot_acc 从 0.3222 提到 0.3778。**压缩率 4.9 倍，指标还涨了 5.6 个百分点**——这是题目「在控制 token 开销的前提下保障关键信息不丢失」最直接的回答。

但要注意：**B2 的 token 数（1,488.9）与 B0/B1 几乎相同**（1,482.2 / 1,457.7），因为预算是硬约束 2,048，所有选择器都填满。**「省 token」这件事在固定预算下不体现为更少的 token，而体现为同样的 token 里装了更多有用的东西**——看 CR：B2 0.7667 vs B0 0.1667，是 4.6 倍。

## 6. 这一层不能证明什么

1. **不能当 JGA 报**。`scenario_success` 是「本场景 2 个槽位全对」，真正的 JGA 需要完整对话状态追踪（DST），0.5B 做不到、API 做完整 DST 也需要另一套 prompt。**绝对 JGA 见 [`L2_JGA校验.md`](L2_JGA校验.md)**（那里用「定向填空」绕过 DST，得到 `full` 0.9174 / `drop_pos` 0.2477）。
2. **180 条样本的统计功效有限**。B2−B1 的 p=0.6964 说明「B2 与 B1 无差异」和「样本不够」这两种解释无法区分。要证明 B2 > B1 需要 500+ 场景。
3. **只有一个 backbone**。`DeepSeek-V4.1-Flash` 的结果不能推广到其他模型。§4.3 的「删噪声有益」在 0.5B 上显著（p=0.0336）、在 API 上不显著（p=0.49），说明**这类结论对模型能力敏感**。
4. **干扰轮是合成的**。真实多会话 Agent 的干扰分布未必与「同领域其他对话的轮次」相同。
5. **没有多轮主循环**。这里每个场景只问一次，没有「答完再看下一步」的交互。题目说的「Agent」在这一点上只是单轮问答 + 记忆模块。

## 7. 复现

```bash
source exp/env.sh && source exp/env.api.sh
python3 exp/scripts/eval_l2.py \
    --n-per-length 30 --max-slots 2 \
    --selectors B0 B1 B2 R0 R1 R2 R3 \
    --tag l2_main_api2
```

约 28 分钟（1,685 秒），产出 `runs/{ts}_eval_l2_l2_main_api2/`：
- `L2_generation.json`：聚合指标（overall / by_length / paired）
- `L2_rows.jsonl`：逐槽位原始记录（含 gold / pred / correct / token）
- `cache.jsonl`：响应缓存（key = sha256(model + prompt + max_tokens)）

`--ar-baseline` 可选 `oracle`（默认）/ `b0full` / `needle`，决定 AR 的分母。**换基准会改变 `ar` 列，但不会改变 `slot_acc`。**
