## 2. 问题拆解：这道题真正在考什么

形式化一下，题目要求的其实是一个**预算约束下的记忆选择**问题：

- 长期记忆库 `M = {m_1, …, m_n}`，每段 `m_i` 有文本、token 数、向量 `e_i`、时间戳；
- 给定当前 query `q` 和 token 预算 `B`；
- 选择函数 `S = Select(M, q, B)`，满足 `tokens(S) ≤ B`；
- 目标：任务完成率 ↑、关键信息召回率 ↑、token 消耗 ↓。

题目指定的打分网络是 `f_θ: R^d → [0,1]`，按 `s_i = f_θ(e_i)` 排序取 top-k 填满预算。所以整条流水线是「**检索召回 → 打分排序 → 预算内截断 → 拼 prompt → LLM 应答**」。

这道题有三个特别容易踩空的地方，而且每一个都直接对应评分点：

1. **"重要" ≠ "新"**。浅层 MLP 只要学会 recency 就能拿到很高的 AUC，方法退化成"滑动窗口 + 时间衰减"，评审一句"这不就是 recency 吗"就能问倒。必须让 `f_θ` 严格赢过 recency 基线。
2. **"重要" ≠ "相似"**。纯向量相似度就是必做要求里的第 2 组基线（B1）。`f_θ` 必须在 B1 之上再涨，否则这个模块白加。
3. **"重要" ≠ "真"**。选做 1 的错误记忆注入正是打这一点：写得越具体、越像关键信息的错误记忆，越容易被打出高分。

**一句话概括本组的方法主张**：在**同等 token 预算**下，`向量检索 + MLP 打分` 的任务完成率与关键信息召回率同时高于「全量上下文」「纯检索」「纯 recency」「随机过滤」四个对照。拿不出这个结论，方法就不成立，要回去改标签而不是改网络。

## 3. 系统设计

### 3.1 总体流程

```
        长期记忆库（按轮切片，带向量与弱监督标签）
        m_1 … m_n
             │
             ▼
  ① 向量检索：cosine 召回 top-M (M=50)
             │
             ▼
  ② MLP 打分：f_θ(e_i) ∈ [0,1]
             │
             ▼
  ③ 预算内选择：按分数降序取，累计 token ≤ B
     （保底：最近 2 轮必留；可选 MMR 去冗余）
             │
             ▼
  ④ 组装 prompt → LLM 应答 → 记录 token 与结果
```

### 3.2 记忆切片

- **粒度：按轮切**，一个 user 轮 + 对应的 system 轮算一段。不切句。
- 理由有三：与 belief state 逐轮对齐（标签可算）、关键信息召回率的判定不依赖分词、与"最近 k 轮"基线口径一致。
- 每段字段：

```json
{
  "mem_id": "MUL0001#t07",
  "dialogue_id": "MUL0001",
  "turn_idx": 7,
  "text": "user: ... system: ...",
  "tokens": 42,
  "embedding": [0.01, ...],
  "ts": 7,
  "slots_delta": {"hotel-name": "acorn guest house"},
  "label": 1
}
```

### 3.3 向量检索

- 编码器：`all-MiniLM-L6-v2`（384 维）。MultiWOZ 是英文语料，**不能用 `bge-small-zh`**（v1 的错误，见附录 A）。
- 相似度：cosine；召回 `M=50`，供打分网络重排。
- embedding 离线算好落盘，评测阶段不重复编码。

### 3.4 打分网络（题目核心）

| 项 | 设计 |
|---|---|
| 输入 | 记忆片段向量 `e_i ∈ R^384` |
| 结构 | `LayerNorm → Linear(384,256) → GELU → Dropout(0.1) → Linear(256,256) → GELU → Dropout(0.1) → Linear(256,1) → Sigmoid` |
| 参数量 | 约 16.5 万，CPU 可训，单轮分钟级 |
| 损失 | 主：`BCEWithLogitsLoss(pos_weight=负/正)`；【建议】附加 pairwise margin ranking loss，因为下游只关心 top-k 的**排序**，不关心绝对概率 |
| 优化 | AdamW，lr 3e-4，batch 256，weight decay 即 L2 项，early stop on val AUC |
| 输出 | 标量分数，`[0,1]` |

【建议】主实验严格只喂 `e_i`，以贴合题目"针对向量表征打分"的表述；把"拼接轮次距离 / 检索分数 / 是否含槽位"作为一组附加特征消融，用来解释增益来源。

### 3.5 预算内选择

- 按分数降序累加 token，超过 `B` 即停。
- **保底规则**：最近 2 轮无条件保留（否则当前对话上下文断裂，模型连"刚才说到哪"都不知道）。这条必须在报告里写明，因为它会削弱 recency 基线的对比优势，不写就是隐藏变量。
- 【建议】top-k 内部用 MMR 做一次去冗余，避免选进 5 段说的是同一件事的记忆。

### 3.6 对话智能体

- backbone：【假设】固定版本的 API 模型，`temperature=0`，`top_p=1`，记录每次调用的 `prompt_tokens / completion_tokens`。
- prompt 模板固定三段：system（角色 + 记忆使用说明）→ memory block（按时间顺序排列的选中记忆）→ 最近轮 + 当前 user。
- **同一模板贯穿所有基线**，只换 memory block 的来源，这是三组对比公平的前提。
- 所有 LLM 响应落盘缓存（按 prompt hash），重跑不重复花钱。

## 4. 数据与标签

### 4.1 MultiWOZ 2.2

- 规模：8438 / 1000 / 1000（train / dev / test），7 个领域（restaurant、hotel、attraction、taxi、train、hospital、police）。
- 单段对话平均【约】13–14 轮，千余 token。
- 2.1 起提供**逐轮** `dialogue_state`（belief state）标注，2.2 修正了部分标注错误——这是弱监督标签的来源。若退回 2.0，则只有 `log` 里的 span 标注，需自行按 span 反推逐轮状态。
- 获取与许可以官方仓库为准（`budzianowski/multiwoz`），报告里注明版本号与 commit。

> **一处必须自己修正的数据问题（2026-11-24 发现）**：官方存储约定是一轮内**先 system 后 user**，所以 `sys_utt[t]` 回复的是 `usr_utt[t-1]`，不是同一轮的 user。三条独立探针确认（test split）：用户问邮编时回复落在 `sys[t+1]` 占 86.1%、落在 `sys[t]` 只占 2.3%；用户提 booking 时确认落在 `sys[t+1]` 381 次 vs `sys[t]` 35 次；`sys` 以问号结尾时短答落在 `usr[t+1]` 1015 次 vs `usr[t]` 514 次。决定性证据是 **turn 0 的 `sys_utt` 在 1000/1000 段对话里都是 `none`**——首轮不存在"上一轮的回复"。
>
> 而状态标注是对齐 user 的（delta 值出现在 `usr[t]` 占 71.8%，出现在 `usr[t-1]` 仅 2.5%）。因此正确的轮次定义是 **`turn t = (usr_utt[t], sys_utt[t+1], states_22[t])`**。若直接取同轮 `sys_utt[t]`，「用户提问 + 系统回复」这一对就是错位的，整段记忆的语义都是错的。`exp/scripts/prepare_multiwoz.py` 已按此修正，原始同轮 system 保留在 `system_raw` 字段备查。

### 4.2 长历史场景构造

**先纠正 v1 的一处硬错误**：v1 写"取同一用户的 8–15 段对话拼接成长期记忆库"。MultiWOZ **没有用户 ID**，跨对话无法归属到同一用户，这个做法在数据上不可实现。

可行方案二选一，**推荐 A**：

- **A. 单对话内膨胀（推荐）**：取一段真实 dialogue，保留其轮次顺序；在关键轮之后、当前 query 之前，插入**同领域其他 dialogue** 的轮次作为干扰。干扰轮与当前任务无关。总长做到 512 轮。
- **B. 跨对话拼接**：把同领域的 8–15 段 dialogue 顺序拼接，视为"同一服务场景下的长期使用记录"，任务只依赖其中 2–3 段。**这是合成设定**，报告中必须明确声明，不能声称是真实用户历史。

**needle 放置**：关键槽位（如 `hotel-name`、`price-range`）在历史中出现一次，之后 80 轮以上不再重复；当前 query 依赖它才能答对。位置**必须随机**（0–90% 分位均匀采样），不能固定在前段——否则位置本身就成了可用特征，模型可以绕过内容直接拿分（§4.3 有实测）。同时放 2–3 个「诱饵槽位」（出现过但已被覆盖的旧值），检验打分网是否只记住了「出现过」而不是「仍有效」。

**关于"上下文溢出"这个前提**：512 轮约 2 万 token，若 backbone 上下文 ≥32k，其实装得下，此时 B0 只是"贵"而不是"装不下"。所以做 **L 扫描**（128 / 256 / 512 轮），报告里给出"随 L 增大，B0 开始截断/性能下降"的曲线——这样"溢出"才是被实验证明的，而不是假设的。

### 4.3 弱监督标签（全题地基）

定义：第 `t` 轮为 **important**，当且仅当

1. 它的 belief state 相对第 `t-1` 轮有**新增或更新**的 slot-value；**且**
2. 该 slot-value 在对话结束时**仍然有效**（未被后续轮覆盖）。

第 2 条是 v1 漏掉的：只看"有变化"会把中间被覆盖的废弃值也标成重要，等于给模型灌噪声。另外排除纯确认轮（"好的""谢谢"）与纯寒暄轮。

**实测**（见 [`exp/data/README.md`](exp/data/README.md)）：正例占比 **55.6%**，不是中度不均衡而是**偏正**。`pos_weight` 不能按「负/正」补偿，否则模型会倾向于全判 1。

**一个必须处理的偏置**：正例率随轮次单调下降（turn 0 为 85%，turn 10 为 16%），仅用「越靠前越重要」这一零成本规则就有 **AUC 0.8065（val）/ 0.8172（test）**。打分网络若只学会「早=重要」而不读内容，也能拿到高分。因此 §5.2 必须加位置基线 R0，§4.2 的 needle 位置必须随机化。

### 4.4 标签校验（反事实删除）

> **已完成（2026-11-23）**，完整结果见 [`exp/docs/反事实删除校验.md`](exp/docs/反事实删除校验.md)。

原方案用 JGA 判定，但 JGA 需要 LLM，而 0.5B backbone 出不了主表（§3）。改用**不需要 LLM 的覆盖率口径**：删掉某组轮次后，query 时刻的 gold 状态里还有多少槽位值能在剩余上下文找到文本支撑。

| 删除条件（等量删 k 轮） | 丢失率（test） |
|---|---|
| 删 label=1（重要） | **26.8%** |
| 删 label=0（不重要） | **3.5%** |
| 删随机（对照） | 19.1% |

**位置混淆已排除**：正例天然集中在开头（平均位置 1.31 vs 负例 3.37），而靠前的轮次更可能是唯一支撑。做位置匹配后差值几乎不变（+0.2610 → +0.2616）；只在 turn 0–2 内比较（位置完全同分布），删正例的丢失率是删负例的 **9.74 倍**；再限制到「正负例在该区间内都有可删轮」的 454 段对话（同分母配对），是 **10.56 倍**。三个 split 一致（配对版 test 10.56× / dev 13.23× / train 10.71×）。

**但标签标的是「引入」不是「必要」**：逐轮看，label=1 轮中有 **42.0%** 不是任何槽位的唯一支撑；用集合覆盖算（能同时删多少），**49.2% 的轮次可删**，其中 **33.3% 的正例不在最小覆盖集里**。注意 42.0% 是逐轮判据，不能直接当可删比例。

**换个标签会更好吗？不会**。按「必要」重定义标签（`label = 唯一支撑`，正例率从 55.6% 降到 32.3%）重训打分器，在 180 个场景上配对比较：CR 0.7778 vs 0.7556，**差值 −0.022、95% CI [−0.083, +0.039]、p = 0.500，不显著**；Recall 反而从 0.637 降到 0.621。83.3% 的场景两者结果完全相同。原因：构造场景时 needle 本就优先选 label=1 的轮次，两个标签对 needle 的判定高度重合，nec 没有额外区分力。**结论：不改标签**，力气应该花在 L=512（CR 只有 0.567）和 L2 上。

**覆盖面**：11.4% 的 gold 槽位不可测（符号值 502、同义表达 289），不进校验。

### 4.4.1 JGA 口径复核（用 LLM 直接判答对）

覆盖率口径只做字符串匹配——信息「还在」不等于 LLM 能「找到并答对」。所以补一层下游效果校验，结果见 [`exp/docs/L2_JGA校验.md`](exp/docs/L2_JGA校验.md)。

0.5B 做不了完整 DST（自造 schema，定向抽取 4/12），但能读上下文做**定向填空**：给含 needle 的上下文答对 0.52，换成「无相关内容」只有 0.04（13 倍差）。因此测**配对**口径而非绝对 JGA。

test split，120 段可配对对话、258 条槽位提问、1371 秒。判对标准是 gold 作为完整词出现：

| 条件 | 全部 258 条 | 可答子集 152 条 | 对话级 JGA |
|---|---|---|---|
| `full` 完整历史 | 0.5891 | 1.0000（定义） | 0.3250 |
| `drop_pos` 删 label=1 | **0.1860** | **0.2632** | **0.0917** |
| `drop_neg` 删 label=0 | 0.6628 | 0.9276 | 0.4000 |
| `drop_rand` 删随机 | 0.4884 | 0.6645 | 0.2750 |

**配对差值（对话级 JGA，5000 次 bootstrap）：drop_pos − drop_neg = −0.3083，95% CI [−0.3917, −0.2250]，p < 0.001。** 在「给全上下文就答对」的 152 条上，删正例答对率从 100% 掉到 26.3%，删负例只掉到 92.8%。

**换成真 backbone 后（DeepSeek-V4.1-Flash，同济 API）**，同一套 607 段 / 1332 条重跑（5328 次生成、1234 秒）：

| 指标 | 0.5B 本地 | DeepSeek-V4.1-Flash |
|---|---|---|
| 可答率 | 0.6134 | **0.9174** |
| 槽位级 `full` | 0.5891 | **0.9174** |
| 对话级 JGA `full` | 0.3250 | **0.8270** |
| 对话级 `drop_pos` | 0.0917 | 0.1598 |
| 对话级 `drop_neg` | 0.6628（槽位级） | 0.8353 |
| **`drop_pos − drop_neg`** | −0.3083 | **−0.6755** CI[−0.7117, −0.6359] p<0.001 |
| 生成耗时 | 4879 秒 | **1234 秒** |

**绝对 JGA 终于可信**（0.5B 的 0.325 是能力上限），而且**标签的区分力大幅增强**：删掉标为重要的那一轮，对话级成功率从 83.5% 掉到 16.0%——**掉了 5.2 倍**。强模型更依赖那一轮，所以标签的价值在强模型上更明显。

**「删噪声有益」在真 backbone 上消失了**（这是原预判的验证，不是意外）：0.5B 时 `full − drop_neg` = −0.075（p=0.0336 显著），API 上 **−0.0082（p=0.49 不显著）**。强模型本来就不容易被噪声干扰。**所以不能拿 0.5B 的「删噪声有益」当结论**——它是小模型特有的现象。

**一个如实报告的意外**：`drop_neg` 的 JGA（0.4000）比 `full`（0.3250）高 7.5 个百分点，这次**显著**（p=0.0336）。方向合理——删噪声减少干扰——但不能当「压缩一定有用」的普适证据。而 `drop_rand` 比 `full` 低 5.0 个点（p=0.278，不显著），因为随机删会删到正例。两者自洽：**删噪声无害甚至微利，删信息有害**。

**两个口径对照**（结论方向一致，测的层面不同）：

| | 覆盖率口径 | JGA 口径 |
|---|---|---|
| 判据 | 槽位值是否还有文本支撑 | LLM 能否答对 |
| 成本 | 1.5 秒 | 22 分钟 |
| 删正例 | 丢失 26.8% | 答对率 100% → 26.3% |
| 删负例 | 丢失 3.5% | 答对率 100% → 92.8% |

**JGA 口径不能证明**：绝对 JGA 不可信（0.5B 的 `full` 只有 0.589，远低于正常 DST 系统）；换 7B / API 后数值会变，但结论方向预期不变；4 个槽位（`train-day`/`restaurant-day`/`train-leaveat`/`hotel-people`，共 15.4%）0.5B 完全答不出，那部分结论是空的。

#### 分槽位细分（607 段对话 / 1332 条槽位，真 backbone）

上面主表是 120 段 / 258 条，够做配对比较，不够分槽位。补跑全量（`--n-dialogues 607`）后，得到一个**比主表更重要的限定**：

| 类别 | 槽位 | n | `full` | `drop_pos` | `drop_pos/full` |
|---|---|---|---|---|---|
| **一次性信息** | 名字 / 类型 / 星级 | 295 | 0.929 | **0.183** | **0.20** |
| **可复述信息** | 区域 / 食物 / 价格 / 日期 / 人数 / 时间 | 1001 | 0.919 | 0.271 | **0.29** |

`drop_pos/full` = 删掉标为重要的那一轮后还剩多少答对率，**越小说明那一轮越不可替代、标签越可靠**。一次性信息只剩 20%，可复述信息还剩 29%——**1.45 倍**。

机制清楚：`anatolia`、`bridge guest house` 这类名字在对话里只出现一次，删了就没了；而 `centre`、`chinese`、`moderate` 会被反复提及，删一轮还能从别处捞到。**所以标签在一次性信息上可靠，在可复述信息上会高估「这一轮的必要性」**——这与 §4.4 的 necessity 分析（42.0% 的正例不是唯一支撑）是同一件事的两种测法。

在 0.5B 上这个差距是 2.3 倍（0.16 vs 0.37），换成真 backbone 后收窄到 1.45 倍——强模型更能从别处推回可复述的值，但**一次性信息仍然推不回来**，方向不变。

**`train-day` 是最有说服力的对照**：0.5B 时 `full` 只有 0.030（131 条对 4 条），换 API 后 **1.000**（131 条全对），而 `drop_pos` 只有 0.199。说明那个 0.030 确实是模型能力不足，不是标签或数据的问题。真 backbone 下仍偏低的只剩 `train-leaveat`（0.238，相对时间表述）与 `restaurant-day`（0.606）。

**第三个口径：模拟抽检 κ**（见 [`exp/docs/标签抽检.md`](exp/docs/标签抽检.md)）。用户没有时间人工判断 60 条，改用两个**独立于标签规则**的判据模拟。必须说明：**这不是人工校验**，它证明的是「标签与两种自动化判据一致」，不是「标签与人一致」。

| 对比 | Cohen's κ | 一致率 | 95% CI |
|---|---|---|---|
| 标签 vs J2（末次提及） | 0.430 | 71.5% | [0.305, 0.550] |
| 标签 vs J3（唯一支撑） | 0.500 | 75.0% | [0.382, 0.608] |
| J2 vs J3（两判据互相） | **0.707** | 85.5% | [0.612, 0.798] |

κ 落在 0.43–0.50 属「中等一致」，两判据互相之间 0.707 属「强一致」——说明标签不是随机的，但也确实存在可观的边界模糊。**报告里「标签可信度」这一节靠覆盖率 + JGA + 模拟 κ 三项站住，并如实标注第三项是模拟值。**

> **一个被证伪的方案**：最初想让 0.5B 直接读对话答 yes/no「这一轮是否必要」。四种写法全部退化——直接问 0.033 正例率（58/60 全答 no）、few-shot 0.100、抽取式 1.000、A/B 选项 0.983，κ 分别为 0.067 / −0.067 / 0.000 / 0.033。**0.5B 没有语义必要性判断能力**，只能被句法形式牵着走。这个负结果本身就是「为什么 JGA 要用填空任务而非 yes/no」的证据。

### 4.5 数据划分（防泄漏）

- **按 `dialogue_id` 划分** train / val / test，绝不按 turn 随机划分。
- 用方案 B 拼接时，同一 dialogue 只能出现在一个 split 里。
- split 文件与随机种子一起提交，保证可复现。

## 5. 实验设计

### 5.1 三组基线（题目指定）

| 组 | 记忆来源 | 选择方式 | 说明 |
|---|---|---|---|
| **B0** | 原始全量上下文记忆 | 全部历史直接塞入，超长则从头截断 | 上限参照，token 会显著超预算 |
| **B1** | 仅向量检索记忆 | cosine top-k 填满预算 B | 无打分模块 |
| **B2** | 向量检索 + MLP 打分 | **全库稠密打分** → 排序 → 填满 B | 本题方法（见下方实测说明） |

**公平性约束（缺一不可）**：同一 backbone、同一 prompt 模板、同一 `B`、同一 test set、`temperature=0`、同一随机种子集。

> **实测修正（2026-11-24，修正 system 错位后重算）**：原方案写的是「检索 top-50 → 打分器重排」的两阶段，实测该设计被**检索召回**卡死。needle 在库内的余弦排名进入 top-50 的比例：
>
> | L | top_m=10 | top_m=20 | **top_m=50** | top_m=100 |
> |---|---|---|---|---|
> | 128 | 0.311 | 0.400 | **0.678** | 0.967 |
> | 256 | 0.244 | 0.322 | **0.456** | 0.689 |
> | 512 | 0.133 | 0.244 | **0.344** | 0.500 |
>
> **B2R 的实测 CR 与这个召回率一一吻合**（0.633 / 0.456 / 0.311），即上界被检索卡死。且召回率随 L 增大而下降——「检索 top-50」在长历史上**越用越差**，与题目目标相反。
>
> 改为**全库稠密打分**后跨长度 CR 达到 **0.7667**。打分器对 8,372 段做一次 batch 推理实测只要 **0.014 秒**，全库打分不构成成本问题。这条要写进报告的「局限与改进」。

**token 口径要报两张表**：(a) 各自自然消耗（B0 很高，B1/B2 受 B 约束）；(b) 强制同预算 B（B0 截断）。只报 (a) 会被质疑"少给 token 当然省钱"。

### 5.2 附加对照（自加，用于防守）

这几条不是题目要求，但不做就无法回答"你的方法凭什么不是启发式"：

| 组 | 做法 | 回答什么问题 |
|---|---|---|
| **R0** | 位置基线：按对话内相对位置从早到晚取（`-rel_pos`） | 模型是不是只学会了"早=重要"（实测 test AUC **0.8172**，最需要防的一条） |
| **R1** | 纯 recency：取最近 k 轮填满 B | 打分网是不是只学会了"越新越重要" |
| **R2** | 随机过滤：随机选，同预算 B | 增益是不是单纯来自"少给 token" |
| **R3** | 打乱时间顺序后重跑 B2 | 模型到底有没有在用时间信息；若打乱后性能不掉，说明它在靠语义而非时序，是好事；若掉很多，说明 recency 泄漏 |

R0 是实测出来的最强启发式（test AUC 0.8172 / val 0.8065，首因偏置：正例率 turn0 85% → turn10 16%），打不赢它就说明模型没读内容；R2 排除「少给 token 自然省事」——没有它，「B2 比 B0 好」完全可能只是上下文短了、噪声少了。

### 5.3 指标定义（题目指定的三个，必须写清口径）

| 指标 | 定义 | 计算 |
|---|---|---|
| **任务完成率** | 当前 query 涉及的目标槽位是否**全部正确**填出 | 逐样本 0/1，取均值；辅助口径：全轮 JGA、ConvLab 模拟器 success（仅 100 段） |
| **token 消耗** | 每次 LLM 调用的 `prompt_tokens` | 报均值 + 总成本；另给"每样本 token"分布 |
| **关键信息召回率** | 两级：**CR** = needle 段是否被选入上下文；**AR** = needle 的槽位值是否出现在最终预测状态 | 主报 AR，CR 用于解释机制 |

补充指标（评估打分网本身，非题目要求）：AUC、NDCG@k、Recall@budget。

### 5.4 消融实验（题目指定三个因素）

单因素扫描，其余固定为默认值（L=2 层，lr=3e-4，L2=1e-4）：

| 因素 | 取值 | 固定 |
|---|---|---|
| 网络层数 | {1, 2, 3, 4} | lr=3e-4, L2=1e-4 |
| 学习率 | {1e-4, 3e-4, 1e-3, 3e-3} | 2 层, L2=1e-4 |
| L2 正则强度 | {0, 1e-5, 1e-4, 1e-3} | 2 层, lr=3e-4 |

- 每组 3 个种子（0/1/2），报均值 ± 标准差，图上画 error bar。
- 输出：3 个指标 × 3 个因素的折线图 + 原始 csv。
- 报告里要回答的是"**为什么默认配置是这个**"，不是"把网格跑完"。

**已跑完的结果（test AUC，3 seeds）**：

| 因素 | 取值 → AUC | 结论 |
|---|---|---|
| 网络层数 | 1→0.9352、2→0.9340、3→0.9341、4→0.9339 | 无显著影响；**1 层（99,585 参数）性价比最优** |
| 学习率 | 1e-4→0.9349、3e-4→0.9340、1e-3→0.9337、3e-3→0.9336 | 无显著影响 |
| L2 强度 | 全部 0.9340 | 完全无影响，说明未过拟合 |

AUC 跨度 0.0013，**与种子间标准差 0.0007 同一量级**。这不是调参失败，是真实结论：384 维 MiniLM 向量里判别所需信号近似线性可分，1 层就够——恰好印证题目「**浅层**全连接神经网络」的设定不是妥协。

### 5.5 选做拓展

**选做 1：错误记忆注入**

- 做法：向记忆库注入与真实状态矛盾的记忆（例：真实是"便宜酒店"，注入"用户坚持要五星级"），且写得具体、信息密度高。
- 观察：`f_θ` 给不给高分？agent 会不会被带偏？
- 预期失效场景：打分网只看"信息量/显著性"，无法验证真伪 → 错误记忆反而得高分。这恰好说明**重要性 ≠ 真实性**，需要一致性校验或来源可信度，是报告里很好的一个讨论点。

**选做 2：摘要压缩**

- 做法：对分数中等、可能相关的片段做 LLM 摘要（每条 ≤ 30 token），替代直接丢弃；对比"硬过滤 vs 摘要压缩"在同 token 预算下的 AR。
- 注意：摘要本身消耗 token 与调用次数，**必须计入成本**，否则对比不公平。

### 5.6 实测结果与失败预案

**L1 选择质量（已跑完，详见 [`exp/docs/L1实验结果.md`](exp/docs/L1实验结果.md)）**。跨长度 CR（needle 是否被选进上下文）：

| 组 | L=128 | L=256 | L=512 | 跨长度 |
|---|---|---|---|---|
| **B2（本题方法）** | **1.000** | **0.767** | **0.533** | **0.7667** |
| LEN（长度基线） | 0.833 | 0.533 | 0.300 | 0.5555 |
| B2R（两阶段，已弃用） | 0.633 | 0.500 | 0.367 | 0.5000 |
| B1（仅检索） | 0.700 | 0.400 | 0.333 | 0.4778 |
| R0（位置基线） | 0.433 | 0.200 | 0.200 | 0.2778 |
| R2（随机） | 0.500 | 0.167 | 0.067 | 0.2445 |
| R3（打乱时序） | 0.467 | 0.100 | 0.033 | 0.2000 |
| B0/R1（时间序截断） | 0.400 | 0.100 | 0.000 | 0.1667 |

- **B2 在三个长度上全部最优**。但**「优势随历史变长扩大」这个说法不成立**：B2/B1 比值 1.43× → 1.92× → 1.60×，B2−B1 绝对差 0.300 → 0.367 → 0.200，都不是单调的。B2/R0 的倍数（2.31× → 3.83× → 2.67×）与 B2−R2 的绝对差（0.500 → 0.600 → 0.467）同样非单调。如实表述：**B2 在各长度稳定领先，但领先幅度不随 L 单调增长**——L=512 时 CR 只有 0.533，是当前最明显的短板。
- **B0 与 R1 完全相同**，这是必然的：没有记忆模块时，"全量上下文"在超预算后就是按时间序从头截断。这本身是个值得写进报告的结论——**B0 不是"更多信息"，只是"更贵的截断"**。
- **LEN 基线意外地强**（0.5555，仅次于 B2）。已在 L1 文档里做了自查：`corr(score, n_tokens)=+0.633`，但按长度四分位分层 AUC 仍为 0.946 / 0.908 / 0.868 / 0.856，说明内容信号独立有效。
- **B2 在 L=128 的 CR=1.000 是满分**，偏乐观，原因是短历史下位置信号与内容信号高度重合。报告里不能只报这个数。

**预算扫描（压缩率 → CR，`n_per_length=20`、2 seeds）**：

| 预算 B | L=128（库 4,497 tok） | L=256（库 8,910 tok） | L=512（库 16,874 tok） |
|---|---|---|---|
| 256 | 0.350 / 0.150 / 0.050（保留 5.7%） | 0.100 / 0.125 / 0.000（2.9%） | 0.050 / 0.075 / 0.025（1.5%） |
| 512 | 0.475 / 0.275 / 0.100（11.4%） | 0.350 / 0.225 / 0.050（5.8%） | 0.225 / 0.100 / 0.050（3.0%） |
| 1024 | 0.875 / 0.350 / 0.150（22.8%） | 0.625 / 0.275 / 0.125（11.5%） | 0.400 / 0.275 / 0.075（6.1%） |
| 2048 | 1.000 / 0.700 / 0.425（45.5%） | 0.900 / 0.325 / 0.200（23.0%） | 0.625 / 0.275 / 0.100（12.1%） |

每格是 **B2 / B1 / R0** 的 CR。结论要分开说，不能一句「全赢」带过：

- **B=1024 与 B=2048 的 6 个格子，B2 全部第一**，且压缩越激进优势越大（L=512、B=1024 时 B2 0.400 vs B1 0.275 vs R0 0.075）。
- **B=256 的 3 个格子里有 2 个 B2 输给 B1**：L=256 时 0.100 vs 0.125、L=512 时 0.050 vs 0.075。这是真实的负结果，不粉饰——**当预算只够放 8–9 个片段时，稠密打分器的排序精度不如余弦相似度**。可能原因是打分器在训练分布上偏向"整体重要性"，而余弦相似度直接对齐 query，极低预算下后者更不容易选错。这个现象值得在报告里单独讨论，而不是当成噪声。
- **R0 在所有 12 个格子里都最差或接近最差**，位置启发式在压缩场景下完全失效。
- **L=512、B≤512 时所有方法都接近 0**，此时任何选择器都救不回来，是「关键信息在极低预算下无法保障」的负结果。

**原预期 vs 实测的偏差**：

| 项 | 原预期 | 实测 | 处理 |
|---|---|---|---|
| 正例率 | 25–40% | **55.6%** | `pos_weight` 方向反了会推向全判 1，已改 `auto`=0.7993 |
| 位置偏置方向 | recency（越新越重要） | **primacy（越早越重要）** | R1 反而成了最差基线之一 |
| 最强启发式 | recency | **位置 + 长度** | 补了 LEN 基线 |
| 两阶段检索 | 提效 | **被召回卡死** | 改全库稠密打分 |
| 优势随 L 扩大 | 假设成立 | **不成立**；对 B1 的比值 1.43/1.92/1.60 非单调 | 正文改为「领先幅度不随 L 单调增长」，不再声称扩大 |
| 原始数据轮次对齐 | 同轮 user↔system | **system 错位一轮**（`sys[t]` 回的是 `usr[t-1]`） | 全部下游重跑，见附录 E |

### 5.7 任务完成率：从「选得对」到「答得对」

**这是题目要求的三个指标里最后一个，也是唯一需要 LLM 的那个。** 完整分析见 [`exp/docs/L2任务完成率.md`](exp/docs/L2任务完成率.md)。

设置：test 90 场景（L=128/256/512 各 30 段对话）× 每场景 2 个槽位 = 180 条；backbone `api:DeepSeek-V4.1-Flash`；预算 B=2048；耗时 1,685 秒。

| 选择器 | slot_acc | 场景成功率 | AR（可答子集） | ctx token | CR |
|---|---|---|---|---|---|
| **B2（本题方法）** | **0.3778** | **0.1667** | **0.4079** | 1,489 | **0.7667** |
| B1（仅检索） | 0.3556 | 0.1000 | 0.3816 | 1,458 | 0.4778 |
| R1（recency） | 0.3278 | 0.1333 | 0.3355 | 1,482 | 0.1667 |
| B0（时间序截断） | 0.3167 | 0.1222 | 0.3224 | 1,482 | 0.1667 |
| R2（随机） | 0.3056 | 0.1111 | 0.3224 | 1,488 | 0.2444 |
| R3（前 3 轮） | 0.2167 | 0.0444 | 0.2171 | 1,502 | 0.2000 |
| R0（位置基线） | 0.2111 | 0.0111 | 0.2171 | 1,485 | 0.2778 |
| **ORACLE（作弊基线）** | **0.8444** | **0.7222** | 1.0000 | **216** | 1.0000 |
| B0FULL（全量上下文） | 0.3222 | 0.0444 | 0.3684 | **7,277** | 1.0000 |
| NEEDLE（只给 needle 轮） | 0.3444 | 0.1333 | 0.4013 | 39 | 1.0000 |

配对比较（按场景×槽位，bootstrap 5000）：**B2−B1 只 +0.0222，p=0.6964，不显著**；B2−B0 +0.0611（p=0.1948）；**B2−R0 +0.1667，p<0.0001，是唯一显著的一对**；B2−R2 +0.0722（p=0.0984，边缘）。

四条必须如实写的结论：

1. **CR 高不等于答对率高**。B2 的 CR 0.7667 是 B0 的 4.6 倍，但 slot_acc 只从 0.3167 到 0.3778。needle 在上下文里、和模型能答对，中间隔着一道鸿沟。
2. **鸿沟来自「跨对话的冲突干扰」**。30 个 L=128 场景里，**33 个（场景,槽位）组合**的选中上下文含「同槽位、不同值」的干扰轮——gold=`centre` 答 `north`、gold=`0` 答 `4`。**纯文本打分器看不到对话边界**，这是它的固有盲区，也是下一步最该改的地方（加 `dialogue_id` 特征或做对话级聚类）。
3. **ORACLE 只用 216 token 就到 0.8444，B2 用 1,489 token 只有 0.3778**。ORACLE 是作弊基线（它知道哪些轮属于本对话），所以这 **46.6 个百分点不是「方法不够好」，而是「任务本身有多难」的上界**——它量化了「区分对话归属」这件事的价值。
4. **B0FULL（7,277 token）只有 0.3222，比 B2 还低，比 ORACLE 低 52 个百分点**。上下文越长、干扰越多，强模型也会被带偏。**这是「记忆过滤」存在理由最直接的证据**——不是为了省 token（虽然确实省了 4.9 倍），而是因为不滤会答错。

**B2 相对 B1 的优势在 L2 上不显著**（p=0.6964），与 L1 上 CR 差 28.9 个百分点形成对比。这不是矛盾：CR 只测「needle 在不在」，而 slot_acc 还要看「干扰轮有没有把答案带偏」。**180 条样本的功效也不够**，要判定需要 500+ 场景。

若出现以下情况，按预案处理，**不要靠调参硬凑**：

| 现象 | 诊断 | 处理 |
|---|---|---|
| B2 ≈ R1 | 打分网退化成 recency | 检查标签是否与轮次强相关；加 R3 打乱顺序对照；改 ranking loss |
| B2 ≈ B1 | 打分网没学到检索之外的信息 | 检查输入是否只有 `e_i` 导致信息不足；加槽位/轮次特征消融 |
| 全部组都很高 | 任务太简单，needle 太好找 | 加大 L、增加诱饵槽位、把 needle 埋到"中间位置"（lost-in-the-middle） |
| 方差大于增益 | 样本量不足 | 扩 test set 到 300+，固定种子，报置信区间 |

负结果也可以写，但必须写清"为什么负"，这比凑一个漂亮数字更符合研究生课程的要求。

### F.2 修复 `hash()` 随机盐（影响所有已跑结果）

**这是本次最严重的一个 bug。**

`exp/src/memory/long_history.py:310` 用 `random.Random((hash((did, L, seed)) & 0xFFFFFFFF))` 生成 `needle_pos`。Python 3 默认对 str/bytes/tuple 的 `hash()` 加**随机盐**（`PYTHONHASHSEED`），**每次进程的 hash 都不同**：

```
$ python3 -c "print(hash('MUL0003.json'))"   # 连跑三次
-1323061345261709640
-5529332290310673915
-2956250011040923084
```

后果：同一份数据 + 同一个 seed，**每次运行生成的长历史场景完全不一样**（`needle_pos` 一次 0.86、一次 0.69），场景 id 带位置后缀 `_p0.80_s0`，连「哪些场景」都对不上，**响应缓存全部失效，L1/L2/budget/necessity 的所有结果不可复现**。

修法：`exp/src/common.py` 新增

```python
def stable_seed(*parts: object, mod: int | None = None) -> int:
    h = hashlib.sha256()
    for x in parts:
        h.update(repr(x).encode("utf-8"))
        h.update(b"\x00")
    v = int.from_bytes(h.digest()[:8], "big")
    return v % mod if mod else v
```

三处替换：`long_history.py:310`、`agent/loop.py:188`（R2 随机基线）、`eval/runners.py:129`（R2）。`test_src.py` 新增 `test_stable_seed()`，用**子进程实测**跨进程一致性（不是只比同进程两次调用——那样测不出随机盐）。现 **48 项全通过**。

修复后 3 个独立子进程得到完全相同的场景 id，L1 / budget / necessity / L2 全部重跑。
