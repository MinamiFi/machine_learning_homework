# L2 JGA 口径校验：删掉「重要」的轮次，LLM 还答得对吗

> 一句话结论：**答不对了。** 在「给全上下文就能答对」的 152 条槽位上，
> 删掉 label=1 的轮次答对率从 100% 掉到 **26.3%**，删掉等量 label=0 的轮次
> 只掉到 **92.8%**。对话级 JGA 口径下两者差 **30.8 个百分点**
> （95% CI [22.5, 39.2]，p<0.001）。
> 这是继覆盖率校验（10.56 倍）之后，用**下游任务效果**独立验证同一结论。
>
> **本文所有数字均基于修正 system 错位后的数据**（见 `exp/data/README.md`）。v5 版本文档的数字已全部作废。

## 0. 为什么还要做这一层

`docs/反事实删除校验.md` 已经用**覆盖率口径**验过标签：删掉 label=1 的轮次后，
gold 状态里有 26.8% 的槽位值再也找不到文本支撑，删 label=0 只有 3.5%。

但覆盖率口径有个本质限制：**它只做字符串匹配**。槽位值在上下文里"还在"，
不等于 LLM 能"找到并答对"——尤其当上下文里有很多干扰、或者值出现多次时。
所以那个校验证明的是「信息没丢」，不是「任务能完成」。

这一层用 LLM 直接回答，测的是**下游效果**。两个口径独立，结论一致才算站得住。

## 1. 为什么是「配对」口径，不是绝对 JGA

根 README §4.4 原方案是「删掉记忆后 JGA 是否下降」。直接算**绝对 JGA**
需要一个会做对话状态追踪的 backbone。本机只有 Qwen2.5-0.5B：

- 让它把整段对话的 slot/value 输出成 JSON → 给出自造 schema
  （`hotel_options` 数组、`U`/`S` 键），与 gold 完全不可比；
- 定向抽取 12 个槽位 → 只中 **4/12**。

所以改测**配对**口径：同一段对话、同一个槽位、同一个模型，只改「上下文里给了什么」。
0.5B 的绝对能力差被四个条件同时扣掉，剩下的差值才是标签带来的。

**前提是它至少会读上下文。** 实测（25 个数字槽位样本）：

| 条件 | 答对 |
|---|---|
| 上下文含 needle | **13/25 = 0.52** |
| 上下文换成「无相关内容」 | **1/25 = 0.04** |

13 倍差 —— 它确实在读上下文，不是瞎猜。这就够了。

## 2. Prompt 是调出来的，不是随手写的

同一批 25 个数字槽位样本，三种问法差 2.6 倍：

| 问法 | 模板 | 答对 |
|---|---|---|
| v1 问答式 | `Question: How many diners...? Answer with the exact value` | 5/25 = 0.20 |
| **v2 填空式** | `Read the context and fill in the blank. Reply with only the missing words.\nThe restaurant table is booked for ___ people.` | **13/25 = 0.52** |
| v3 格式约束 | `Extract from the context. Output format: <answer only>` | 9/25 = 0.36 |

失败模式很清楚：**问答式的问句里自带数字**（"for how many people"），0.5B 会把问句
本身回显出来当答案。填空式把"要填的位置"和"问的是什么"分离，模型只需补词。

所以 `src/agent/prompt.py` 的 30 个 `SLOT_BLANK` 模板**一律不含数字**。这是硬约束。

## 3. 实验设置

- **样本**：test split，从「可配对」对话中取 **120 段**，共 **258 条槽位提问**。
  「可配对」= 删正例会丢掉该槽位、删负例不会丢，这样四条件才比得出东西。
- **四条件**（每条件同一批槽位，只改上下文）：
  - `full` — 完整历史（上界）
  - `drop_pos` — 删 k 个 label=1 轮
  - `drop_neg` — 删 k 个 label=0 轮（位置与正例尽量匹配）
  - `drop_rand` — 删 k 个随机轮
  - k = min(n_pos, n_neg)，四条件删除量相同
- **backbone**：Qwen2.5-0.5B-Instruct，`do_sample=False`，`max_new_tokens=24`
- **判对**：gold 作为**完整词**出现在预测里（数字要求独立出现，`4` 不命中 `14`）
- **成本**：1032 次生成，**1371 秒**（22.8 分钟），2 核 CPU
- **缓存**：全部落 `runs/*/cache.jsonl`，换匹配规则重算只需 0 秒（见 §7）

## 4. 结果

### 4.1 槽位级准确率

| 条件 | 全部 258 条 | 可答子集 152 条 |
|---|---|---|
| `full` | 0.5891 | **1.0000**（定义） |
| `drop_pos` | **0.1860** | **0.2632** |
| `drop_neg` | 0.6628 | **0.9276** |
| `drop_rand` | 0.4884 | 0.6645 |

**可答子集**（给全上下文就答对的 152 条，占 58.9%）是干净的对比：
删正例答对率掉到 **26.3%**，删负例只掉到 **92.8%**，**差 3.5 倍**。

全量 258 条里 `full` 只有 0.589，是因为 0.5B 对部分槽位即使给全上下文也答不出
（`train-day` 0.036、`restaurant-day` 0.200、`hotel-people` 0.200、`hotel-pricerange` 0.286）。
这些行会同时稀释四个条件，所以必须单独报可答子集。

### 4.1.1 换成真 backbone（DeepSeek-V4.1-Flash）后的绝对 JGA

> 上面 §4.1 是 0.5B 的结果。0.5B 只能做配对比较（`full` 只有 0.589），
> 绝对数字没有意义。接上同济 API 后重跑同一套 607 段 / 1332 条，
> 拿到了可信的绝对 JGA。

**`exp/runs/20261124_081620_jga_api_full/`**，`api:DeepSeek-V4.1-Flash`，
5328 次生成、**1233.8 秒**（并发 3）。

| 指标 | 0.5B 本地 | DeepSeek-V4.1-Flash |
|---|---|---|
| 可答率（`full` 答对比例） | 0.6134 | **0.9174** |
| 槽位级 `full` | 0.5891 | **0.9174** |
| 槽位级 `drop_pos` | 0.1860 | 0.2477 |
| 槽位级 `drop_neg` | 0.6628 | 0.9204 |
| 对话级 JGA `full` | 0.3250 | **0.8270** |
| 对话级 JGA `drop_pos` | 0.0917 | 0.1598 |
| `drop_pos − drop_neg`（对话级） | −0.3083 | **−0.6755** |
| 生成耗时 | 4879 秒 | **1234 秒** |

**三件事变了，两件事没变。**

变了：

1. **绝对 JGA 从 0.827 起跳，终于可信**。0.5B 的 0.325 是能力上限，不是标签的问题。
2. **标签的区分力大幅增强**：`drop_pos − drop_neg` 从 −0.3083 扩大到 **−0.6755**
   （CI [−0.7117, −0.6359]，p<0.001）。删掉标为重要的那一轮，对话级成功率从
   83.5% 掉到 16.0%——**掉了 5.2 倍**。强模型更依赖那一轮，所以标签的价值在强模型上更明显。
3. **「删噪声有益」消失了**：`full − drop_neg` 从 −0.075（0.5B 时显著，p=0.0336）
   变成 **−0.0082（CI [−0.0297, +0.0132]，p=0.49，不显著）**。这正是 §6 第 5 条
   预判的：强模型本来就不容易被噪声干扰，删掉冗余对它既无益也无害。

没变：

1. **方向**：删正例必崩、删负例几乎无损。两个 backbone 完全一致。
2. **一次性信息比可复述信息可靠**：一次性 `drop_pos/full` = **0.20**、
   可复述 **0.29**。差距从 0.5B 的 2.3 倍收窄到 **1.45 倍**，但方向不变——
   强模型能从别处推回可复述的值，一次性信息仍然推不回来。

**`train-day` 是这次最有说服力的对照**：0.5B 时 `full` 只有 0.030（131 条对 4 条），
换 API 后 **1.000**（131 条全对），而 `drop_pos` 只有 0.199。说明之前那个 0.030
确实是模型能力不足，不是标签或数据的问题。

### 4.2 对话级 JGA（该对话抽到的槽位全对）

| 条件 | JGA |
|---|---|
| `full` | 0.3250 |
| `drop_pos` | **0.0917** |
| `drop_neg` | **0.4000** |
| `drop_rand` | 0.2750 |

配对 bootstrap（5000 次，按对话重采样）：

| 对比 | 差值 | 95% CI | p |
|---|---|---|---|
| **drop_pos − drop_neg** | **−0.3083** | [−0.3917, −0.2250] | **<0.001** |
| drop_pos − drop_rand | −0.1833 | [−0.2583, −0.1083] | <0.001 |
| drop_neg − drop_rand | +0.1250 | [+0.0417, +0.2083] | 0.0024 |
| **full − drop_neg** | **−0.0750** | [−0.1417, −0.0083] | **0.0336** |
| drop_rand − full | −0.0500 | [−0.1333, +0.0333] | 0.2784 |

### 4.3 「删掉不重要的轮次反而更好」——在 0.5B 上成立，在真 backbone 上不成立

**0.5B**：`drop_neg`（0.4000）比 `full`（0.3250）高 **7.5 个百分点，p=0.0336，显著**。
删掉无关轮次确实能减少干扰，让 0.5B 更专注。

**DeepSeek-V4.1-Flash**：`drop_neg`（0.8353）比 `full`（0.8270）高 **0.8 个百分点，
p=0.49，不显著**。效应消失了。

**这个消失是预期的，不是坏消息**（§6 第 5 条早就预判了）：强模型本来就不容易被噪声干扰，
删掉冗余对它既无益也无害；小模型容量有限，噪声会挤占注意力，所以受益明显。

**结论要按 backbone 分开说**：
- 0.5B：删噪声有益（+7.5pp，显著）
- 强模型：删噪声无害也无益（+0.8pp，不显著）

**不能拿 0.5B 的数字当普适结论**。报告里如果引这条，必须写清是哪个 backbone。
至于「我们的打分器有用」，那是 `drop_pos` vs `drop_neg` 那行的事（−0.6755，p<0.001）。

### 4.4.1 从这张表读出的四件事

1. **一次性信息比可复述信息可靠，真 backbone 上依然成立。**

   | 类别 | 槽位 | n | `full` | `drop_pos` | `drop_pos/full` |
   |---|---|---|---|---|---|
   | 一次性 | 名字 / 类型 / 星级（`restaurant-name`、`attraction-name`、`hotel-name`、`hotel-type`、`attraction-type`、`hotel-stars`） | 295 | 0.929 | **0.183** | **0.20** |
   | 可复述 | 区域 / 食物 / 价格 / 日期 / 人数 / 时间 / 车次 | 1001 | 0.919 | 0.271 | **0.29** |

   删掉标为重要的那一轮，一次性信息只剩 20% 答对率，可复述信息还剩 29%——**1.45 倍**。
   0.5B 上是 2.3 倍，强模型把差距收窄了（它更能从别处推回可复述的值），
   但**方向没变**：`anatolia`、`bridge guest house` 只出现一次，删了就推不回来；
   `centre`、`chinese`、`moderate` 会被反复提及。

   **这是分槽位表最有价值的产出，也是对整个标签方案最重要的限定**：
   标签在一次性信息上可靠，在可复述信息上会高估「这一轮的必要性」。
   报告里应当这样写，而不是笼统说「标签可信」。

2. **`train-day` 是最有说服力的对照**：0.5B 时 `full` 只有 0.030（131 条对 4 条），
   换 API 后 **1.000**（131 条全对），而 `drop_pos` 只有 0.199。
   说明 0.5B 那个 0.030 确实是**模型能力不足**，不是标签或数据的问题。
   同类修复：`hotel-people` 0.200 → 0.850、`restaurant-name` 0.883 → 0.933。

3. **`train-leaveat`（0.238）与 `restaurant-day`（0.606）是真 backbone 下仍然偏低的两个槽位**。
   `train-leaveat` 的问题在数据本身：MultiWOZ 里「出发时间」常用相对表述
   （"in 10 minutes"、"after 5 pm"），而 gold 是绝对时间（"10:15"），
   模型从上下文推不出换算关系。`restaurant-day` 类似（"the day after tomorrow"）。
   这两个槽位的 JGA 结论要打折看。

4. **`restaurant-area`（n=91）的 `drop_pos/full` 是 0.44，为全表最高之一**。
   区域类值（`centre`、`north`、`east`）在 MultiWOZ 里出现频率极高，删掉标为重要的那一轮
   还有四成概率从别处答对。这是「标签标的是引入，不是必要」在槽位层面的直接体现
   （与 §4.2 的 necessity 分析一致：`redundant_pos_rate` = 42.0%）。

## 5. 两个口径对照

| | 覆盖率口径 | JGA 口径（本节） |
|---|---|---|
| 判据 | 槽位值是否还有文本支撑 | LLM 能否答对 |
| 成本 | 1.4 秒 | 22.8 分钟 |
| 删正例 | 丢失 26.8% | 答对率 100% → 26.3% |
| 删负例 | 丢失 3.5% | 答对率 100% → 92.8% |
| 差距 | **10.56 倍**（同分母配对后） | **3.5 倍**（可答子集） |

**方向完全一致**：标签标为「重要」的轮次，删掉后信息会丢、任务会失败；
标为「不重要」的删掉后基本无影响。两个独立口径都支持这个结论。

## 6. 这个校验不能证明什么

1. **0.5B 的绝对 JGA 不可信**（`full` 只有 0.589），只有配对差值有意义。
   **真 backbone 上绝对 JGA 已经可信**（`full` 0.9174，§4.1.1），
   但那是 607 段测试集上的数字，换领域要重跑。
2. **已换成真 backbone 验证过**（DeepSeek-V4.1-Flash，§4.1.1）：
   `full` 从 0.589 升到 0.9174，标签差距从 −0.3083 扩大到 **−0.6755**。
   结论方向不变、幅度更大——强模型更依赖被标为重要的那一轮。
3. **主表的 258 条槽位 / 120 段对话只够做配对比较**，不够做分槽位细分。
   分槽位用的是扩样后的 1332 条 / 607 段（§4.4），但扩样版没有重算主表——
   两版的主表结论一致（`drop_pos−drop_neg` 初版 −0.3083、扩样 −0.3180），
   所以主表保留初版数字，不混用。
4. **真 backbone 下只剩 2 个槽位偏低**（`train-leaveat` 0.238、`restaurant-day` 0.606），
   原因在数据表述（相对时间 vs 绝对时间），不在标签。0.5B 时那 4 个「答不出」的槽位
   （共 15.4%）大多已被修复：`train-day` 0.030 → 1.000、`hotel-people` 0.200 → 0.850。
5. **「删噪声有益」在真 backbone 上消失了**（这是原预判的验证，不是意外）：
   0.5B 时 `full − drop_neg` = −0.075（p=0.0336 显著），API 上 **−0.0082（p=0.49 不显著）**。
   强模型本来就不容易被噪声干扰，删掉冗余对它既无益也无害。
   **所以不能拿 0.5B 的「删噪声有益」当结论**——它是小模型特有的现象。

## 7. 复现

```bash
source exp/env.sh
# 主实验，约 23 分钟
python3 exp/scripts/jga_check.py --n-dialogues 120 --max-slots 3 --tag jga_main_fix2
# 换匹配规则重算，复用缓存，0 秒
python3 exp/scripts/jga_check.py --n-dialogues 120 --max-slots 3 \
    --resume 20261124_023556_jga_main_fix2 --tag jga_main_fix3
```

产物：`runs/20261124_023556_jga_main_fix2/{jga.json, report.md, cache.jsonl}`。

**踩过的坑**：

1. **撇号归一化**。`Queen's College` 若把 `'` 换成空格会变成 `queen s college`，
   与 gold `queens college` 对不上，造成假阴性。修正：撇号**直接删除**。
   修完 `full` 从 0.5851 升到 0.5934（+8 条，旧数据）。
2. **`"the "` 全局替换**。原来写 `.replace("the ", " ")` 会误伤句中冠词和
   `theatre` 这类词。改成只去**开头**的冠词。
3. **懒加载**。换匹配规则重算时全部命中缓存，不需要加载 3.2 GB 模型。
   `LazyLLM` 包装后重算耗时 0 秒。
4. **模型路径**。`configs/agent.yaml` 里写的是相对路径 `models/Qwen2.5-0.5B-Instruct`，
   必须用 `path_of()` 解析到 exp 根目录，否则 transformers 会当成 HF repo id 去联网。
5. **`attention_mask`**。Qwen 的 pad_token == eos_token，不传 mask 会警告；
   `add_generation_prompt=True` 必须加，否则输出以 `user\n` 开头污染答案。
6. **`--resume` 的路径**。必须写成 `path_of("runs", args.resume) / "cache.jsonl"`，
   直接用相对路径会找不到。

## 8. 对报告的意义

§4.4 的标签可信度现在有**三个独立口径**支撑：

- 覆盖率口径（零成本、全量）：删正例丢 26.8%，删负例丢 3.5%，同分母配对 **10.56 倍**
